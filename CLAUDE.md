# Project Operating Instructions

This file contains the main and permanent operating instructions for the project. Claude Code uses this file directly. Codex is directed to this file via `AGENTS.md`.

## Using Project Context

- At the start of every task, read `context/README.md`.
- Read the files specified as "read in every task" on the main map.
- Read other context files specified on the map as needed based on the topic of the task.
- Do not unnecessarily load files into context that are unrelated to the task.
- Base project information on the verified and current files under `context/`.
- If context files contradict each other or if you doubt their currency, do not choose silently; inform the user.

## Maintaining the Context Map

- If you create, move, rename, change the purpose of, or delete a context file under `context/`, update the `context/README.md` map within the same operation.
- If only the content of a context file has changed and the purpose of the file remains the same, do not modify the main map.
- Ensure that every context file is accessible from the main map directly or through a sub-map.
- If you notice a context file missing from the map, add it to the map if its purpose is clear; if ambiguous, ask the user.
- Do not consider a context-related task complete until the necessary map update is finished.

## Managing Resources

- Treat files under `context/resources/` as reference inputs provided by the user or project.
- If you add, move, rename, or delete a resource, update `context/resources/resource-index.md` within the same operation.
- Do not change the original content of resources unless explicitly requested.
- Do not record outputs, commentary, or summaries generated by the agent as raw resources.
- Once a permanent result extracted from a resource is verified by the user, record it in the relevant context file along with the resource path and time period.
- Do not create a new resource entry in the resource index unless a new resource is added by the user.
- Do not add sensitive information such as passwords, access keys, or unnecessary personal data to the project context.

## Keeping Project Memory Up to Date

- If a goal, decision, rule, scope, boundary, or other permanent project information explicitly changes during a task, update the relevant context file within the same task.
- If it is ambiguous whether information is temporary or permanent, ask the user before adding it to the context.
- Do not record temporary conversations, rejected options, or unverified assumptions as permanent context.
- Do not copy entire chat histories into context files; process only finalized information that will be reused in the future.
- When the user says "update memory", "audit context", or "audit resources", use the `project-memory` skill.
- If important information not yet recorded in permanent context accumulates during a long conversation, ask the user at an appropriate time whether they want to update the memory.

## Working Approach

- Before starting work, inspect the request, relevant files, and existing structure.
- Preserve the user's existing work and modify only the areas necessary for the task.
- Do not modify files outside the task scope.
- Explicitly state any assumption that significantly affects the outcome.
- If there is ambiguity that would change the outcome, ask the user; for minor details, proceed by making reasonable decisions.
- Do not present unverified claims regarding current or external events as absolute facts.

## Authority and Safety

- Do not perform actions that are difficult to reverse, may cause data loss, or have external impact without explicit authorization.
- Verify target and scope for operations like deleting files, overwriting existing content, publishing, sending external messages, or creating payments.
- Do not unnecessarily ask for re-confirmation for safe operations explicitly requested by the user that fall within the task scope.
- Do not disclose secret information in responses, logs, or project documentation.

## Verification and Completion

- Before reporting work as complete, check the outcome in a manner appropriate to the task's risk.
- If it is a software project, use existing test, lint, and build commands (`npm run dev`, `npm run build`, `npm run lint`); do not invent commands.
- If it is a document, analysis, or content project, review the outcome in terms of resources, context rules, and requested formatting.
- Do not represent an unverified point as checked.
- Upon completion, briefly report the changes made, affected files, and unverified points.

## Communication

- Follow the user's language and level of knowledge.
- Provide the result first, followed by necessary explanations.
- Use technical terms only when necessary, and explain them simply upon first use.
- Do not hide ambiguities, assumptions, or obstacles.

## Project-Specific Permanent Instructions

- **Tech Stack**: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, `next-intl`.
- **Development Server**: `npm run dev`
- **Build Verification**: `npm run build`
- **Lint Verification**: `npm run lint`
- Refer to `AGENTS.md` for Next.js agent rules.
